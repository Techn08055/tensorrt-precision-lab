# Conv2D

Second CUDA-kernel module: take real convolutions out of `resnet/` and run them as
GEMMs, starting from the heaviest layers in the per-layer profiles in `../profiling/`.
Builds on [`../gemm/`](../gemm/); see the repo root [`README.md`](../README.md).

## Status

- [x] `Conv_846` (slowest layer in every FP32/FP16/INT8 profile): 1x1 conv, stride 2, 1024x14x14 → 2048x7x7, which is a GEMM with M=2048, N=49, K=1024 after packing the stride-2 pixels — [`src/conv846_gemm.cu`](src/conv846_gemm.cu) (reuses the step-4 WMMA kernel from `../gemm/` unchanged), [`benchmarks/torch_conv.py`](benchmarks/torch_conv.py) (cuDNN baseline), [`results/conv846_gemm.csv`](results/conv846_gemm.csv). FP16, batch 1, no bias, random data at the real shape. Gather + WMMA GEMM: 0.070 ms; gather + cuBLAS: 0.037 ms; cuDNN `conv2d`: 0.027-0.035 ms; TensorRT FP16 layer (from the profile, with bias): 0.043 ms. The gather is 0.003 ms; the gap is the GEMM. Both GEMM outputs are within FP16 rounding of an FP32 CPU conv reference
- [x] Verified on real ResNet50 tensors — [`benchmarks/export_conv_real.py`](benchmarks/export_conv_real.py) runs a real calibration image through the ONNX model in onnxruntime and dumps `Conv_846`'s actual input activation, weights, bias and ONNX's own FP32 output to `data/Conv_846/` (gitignored, regenerate with the script); `./conv846_gemm ../data/Conv_846` uses them. Output + bias matches ONNX within 0.0063 at values up to 14.8 (under one FP16 step at that magnitude) — [`results/conv846_gemm_real.csv`](results/conv846_gemm_real.csv)
- [x] Fit the GEMM to the skinny shape. Padding N 49 → 64 (zero columns, so B gets vectorized loads): 0.070 → 0.054 ms. Probe: 2x the columns (32 → 64 blocks) costs only 1.43x the time, so the GPU is underfilled at 32 blocks. Split-K (K sliced across `blockIdx.z`, FP32 partials, then one reduce kernel that adds bias and writes the final 2048x7x7 NCHW output): best at 4 splits / 128 blocks, **0.039 ms for gather + GEMM + reduce + bias**, against 0.037 ms for gather + cuBLAS (no bias) and 0.043 ms for the TensorRT FP16 layer in the profile. 8 splits: 0.041 ms; 16: 0.050; 32: 0.070. Same numbers on random and real data, three runs within 1%
- [x] Fold the stride-2 gather into the split-K kernel's B tile load (`gemm_wmma_splitk<true>`, reads the raw 1024x14x14 input, no gather kernel, no packed buffer): correct (same 0.0062 max error vs ONNX), but **slower**: 0.042 ms against 0.039 ms with the separate gather at the best 4 splits, and slower at every split count except 32. My reading, not profiled: the folded load is 16 scalar stride-2 loads per thread per k-step instead of 2 16-byte loads, and all 32 row-blocks redo that gather for the same B tile, while the separate gather kernel does it once for 0.003 ms. Kept the separate gather as the default
- [x] `Conv_850` (3x3, stride 1, pad 1, 512x7x7 → 512x7x7; `Conv_856` has the same shape): explicit im2col (k = ci*9 + kh*3 + kw, which is the ONNX weight layout, so W is used as-is; first version, see the speed-up below) into a 4608x64 buffer (590 KB), then the split-K kernel from `conv846_gemm.cu` (included, not copied), then reduce + bias — [`src/conv850_gemm.cu`](src/conv850_gemm.cu), [`results/conv850_gemm_real.csv`](results/conv850_gemm_real.csv). Real tensors: matches ONNX within 0.0040 at values up to 12.1. Only 8 row-blocks without split-K (0.205 ms); best at 12 splits / 96 blocks: **0.047 ms**, level with im2col + cuBLAS (0.047 ms, no bias). im2col alone is 0.009 ms, ~19% of the total. cuDNN via PyTorch: 0.093-0.098 ms; TensorRT FP16 layer in the profile (with bias + ReLU fused): 0.038 ms. Three runs within 1%
- [x] Speed up the im2col pass. `im2col_3x3_v2` (one thread per input channel x pixel writes all 9 taps; 128 blocks of 256 instead of 4,608 of 64) builds a byte-identical buffer 3x faster (0.0068 → 0.0023 ms), and the layer goes from 0.036 to **0.031 ms** at 12 splits, level with im2col_v2 + cuBLAS (0.031 ms, no bias). Implicit GEMM (`gemm_wmma_splitk<2>`: im2col done inside the B tile load, reads the raw 512x7x7 input, no buffer): correct, 0.033 ms, **6% slower** than the separate fast im2col, same direction as the `Conv_846` folding result. Same-run comparisons only: the GPU ran ~30% slower in the first of three runs and switched speed partway through it, so only the second and third runs (within 1%) are quoted; `Conv_846` rechecked unchanged after the shared kernel's load modes became an int template
- [x] Where `Conv_850`'s time goes (Nsight Systems kernel trace of `./conv850_gemm`, 55-56 samples each; the GPU ran at its slower clock during the trace, so the total reads 41 µs instead of 31): im2col_v2 2.4 µs (6%), split-K GEMM at 12 splits 34.4 µs (84%), reduce + bias 2.8 µs (7%), launch gaps 1.4 µs (3%). cuBLAS on the same problem runs the same structure internally — `cutlass_75_tensorop_f16_s1688gemm` with 7 K-splits (34.8 µs) plus its own `splitKreduce_kernel` (2.7 µs) — so our GEMM core is level with cuBLAS's, and the remaining lever is the GEMM core itself
- [x] `Conv_856` and `Conv_842` (3x3, stride 2, 512x14x14 → 512x7x7) through the same driver, now [`src/conv3x3_gemm.cu`](src/conv3x3_gemm.cu) (`./conv3x3_gemm ../data/Conv_842 2`; stride is a parameter of both im2col kernels; implicit-GEMM mode skipped for stride 2). ReLU added to the reduce kernel as a flag: same time, matches ReLU(ONNX) within 0.0021-0.0031. All three 3x3 layers: best at 12 splits, **0.031 ms with bias + ReLU**, level with im2col_v2 + cuBLAS. Results: [`results/conv842_gemm_real.csv`](results/conv842_gemm_real.csv), [`results/conv850_gemm_real.csv`](results/conv850_gemm_real.csv), [`results/conv856_gemm_real.csv`](results/conv856_gemm_real.csv). Our driver's timings come out at either ~0.031 or ~0.041 ms from one process to the next (the GPU's clock state, not the code: every variant in a run shifts together), so the fast-state number is quoted
- [x] TensorRT timed the same way — [`benchmarks/trt_single_layer.py`](benchmarks/trt_single_layer.py), [`results/trt_single_layer.txt`](results/trt_single_layer.txt): one-layer FP16 engines built from the same real weights (conv + ReLU where the full engine fuses one), NCHW FP16 in/out. **TensorRT is ~2x faster than ours on all four layers**: 0.015-0.018 ms (CUDA-graph replay; 0.017-0.021 back-to-back) against our 0.031 ms (3x3) and 0.039 ms (`Conv_846`), even though each engine also runs an NCHW→NHWC and an NHWC→NCHW copy kernel. So the per-layer-profiler figures used above (0.038-0.043 ms) overstate TensorRT's time by ~2x, and the earlier "level with / just under TensorRT" readings were wrong. TensorRT's chosen kernels are `sm80_xmma_fprop_implicit_gemm_*_nhwckrsc_nhwc` (implicit GEMM in NHWC, multi-stage pipelined, 64x32 to 64x128 tiles, no split-K) with `f16f16_f16f16_f16` in the name, i.e. FP16 accumulation; its error against ONNX is 0.037-0.060, ~10x ours. Tested one explanation: cuBLAS on our im2col buffer with `CUBLAS_COMPUTE_16F` is **not** faster than with FP32 accumulation (0.0413 vs 0.0414 ms) and its error rises 0.0057 → 0.013, so FP16 accumulation alone doesn't account for it in cuBLAS. Not yet isolated: NHWC layout, pipeline depth, or FP16 accumulation inside our own kernel
- [x] What TensorRT's ~2x came from (`Conv_850`, all numbers same-run, three runs within 1%, then checked on `Conv_856`/`Conv_842`):
  1. **Hardware:** FP16 accumulation runs the tensor cores at exactly 2.00x the FP32-accumulate rate on this GPU at every block count — [`../gemm/profiling/mma_rate.cu`](../gemm/profiling/mma_rate.cu), [`../gemm/profiling/mma_rate.txt`](../gemm/profiling/mma_rate.txt). Peak is ~2.8 TFLOPS per SM with FP32 accumulation (~55.7 for all 20 SMs; ~42 when the GPU is in its slower clock state, the same 1.33x as our 0.041 vs 0.031 ms runs). Our 0.031 ms kernel ran at ~7.4 TFLOPS, ~13% of that, so it wasn't limited by tensor-core math
  2. **FP16 accumulators in our kernel** (`gemm_wmma_splitk<0, half>`): no gain at the best 12 splits (0.0314 vs 0.0313 ms), 7% at 1 split, error 4.5x higher (0.0021 → 0.0095 after ReLU). Not the cause on its own
  3. **`cp.async` pipeline** (`gemm_wmma_splitk_pipe<STAGES>`, the next tiles copy into shared memory while the current one is computed): 0.152 → 0.080 ms at 1 split (8 blocks), 0.0314 → 0.0278 ms at 12 splits. Two stages are as good as or better than three or four
  4. **Padded shared-memory rows** (`PAD = 8` halves, so the 16 rows a fragment load reads don't start in the same banks): **0.0278 → 0.0215 ms** at 12 splits, 0.080 → 0.060 ms at 8 blocks. Biggest single step. With padding, FP16 accumulators help at 8 blocks (0.060 → 0.046-0.048 ms) but only 2% at 12 splits (0.0211 ms), so FP32 accumulation stays the default
  5. **Result:** all three 3x3 layers at **0.0215-0.0218 ms with bias + ReLU** (2 stages, pad 8, 12 splits, FP32 accumulators, error vs ReLU(ONNX) 0.0021-0.0031), **1.46x faster than im2col + cuBLAS** and ~1.45x behind TensorRT's 0.015 ms (was 2.1x). Nsight Systems split of the 0.0215 ms path (trace taken in the slower clock state, so shares only): GEMM 76%, im2col 9%, reduce 10%, launch gaps 5%. TensorRT does the same work in one conv kernel plus two layout copies, so roughly half the remaining gap is our extra im2col/reduce kernels and half the GEMM kernel itself — estimated from the shares, not measured kernel-for-kernel, because the TensorRT trace is dominated by its tactic-timing runs

- [x] **No padded copy for 1x1 stride-1 layers, and the GEMM writes the final output when it uses 1 split** (`gemm_wmma_splitk_pipe` gained `ldb`/`n_real`/`BVEC`/`EPI`; `./conv_gemm <dir> [nodirect] [noepi]` turns each off). - [x] **Implicit GEMM for 3x3 layers** (`gemm_wmma_splitk_pipe<..., KS = 3>`): the B tile is gathered from the 3x3 windows of the raw input while loading, so no im2col buffer; weights stay on `cp.async`, and the gather is register-prefetched (tile t+2 loaded into registers while tile t computes, written to shared memory after). The driver times explicit im2col and implicit for every 3x3 layer and keeps the faster (`noimplicit` turns it off). Same-run, explicit vs implicit: 56x56 (64 output channels, 1 row-block) implicit **1.35x faster**; 28x28 1.10x; stride-2 from 56x56 1.07x; 14x14 0.82x and 7x7 0.77x slower (4-8 row-blocks each re-gather the same input tile, and the gather is single-value loads). Without the register prefetch it was 1.25x / 0.98x / 0.80x / 0.72x. All 53 layers rerun ([`results/all_layers.csv`](results/all_layers.csv), previous: [`results/all_layers_v2.csv`](results/all_layers_v2.csv)): implicit picked for 7 layers (all 3x3 at 56x56 and 28x28 + `Conv_778`), 3x3 @56 group 0.131 → 0.090 ms, im2col total 0.247 → 0.128 ms, sum 1.084 → 1.056 ms, all match ONNX.
